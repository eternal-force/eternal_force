## 補充說明

- REQ-001：資料庫的 `class_records.duration_minutes` 欄位刻意保留未刪除，因專案目前僅用 `flask init-db`(`db.create_all()`)建表，沒有 Alembic / Flask-Migrate 等版本化遷移工具，刪除欄位需要手動 `ALTER TABLE`，風險與效益不成比例，故僅停用讀寫、不動既有 schema。
- REQ-002／REQ-003：這兩項變更皆對既有的 Supabase(PostgreSQL)資料表新增欄位(`class_records.coach_id`、`class_exercises.weight_kg`/`sets`/`reps`/`note`)。由於同樣沒有遷移工具，已直接對目前連線中的資料庫執行等冪的 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`；若日後切換到新的資料庫(例如正式環境 Render 上的 Supabase 專案)，`flask init-db` 建立的全新資料表會直接包含這些欄位，但**既有**資料庫仍需比照手動補跑一次相同的 `ALTER TABLE`陳述式，否則會出現「欄位不存在」的錯誤。長期建議依 README 既有規劃導入 Flask-Migrate / Alembic，避免每次改 schema 都要手動介入。
- 上課教練下拉選單目前資料來源是「角色為教練且帳號狀態為啟用中」的使用者；若系統中尚無任何教練帳號，選單會是空的，需先透過「帳號管理 → 新增教練」建立至少一位教練帳號，新增上課紀錄功能才可用。
- REQ-008：需求原文提到學生編輯自己資料時「無法修改角色」，但「角色」(`role`：admin/coach/student)是 `User` 帳號的屬性，`students/edit` 這個表單編輯的是 `Student`(學生名冊)資料，本來就不含角色欄位、也從未讓使用者在此表單變更角色。表單中唯一具治理性質、對應「身份/資格」的欄位是「在籍狀態」(`status`：在籍/停用)，因此依此推斷需求實際指的是這個欄位，並依此實作限制；若之後發現需求其實是指別的欄位或別的頁面，請再告知以修正。
- REQ-005：刪除帳號會**連同對應的學生名冊一併硬刪除**(而非僅解除連結)，因為需求描述本身即以「該帳號對應的學生列表是否還有剩餘課程」作為是否允許刪除的判斷依據——若刪除帳號後學生名冊仍保留，這個檢查就沒有意義。若日後只想刪除登入帳號、保留學生歷史資料，需另外調整此邏輯(可參考既有 `delete_student_hard` 僅解除連結、不刪學生的做法)。
- REQ-006：`User.phone_type` 為新增欄位，比照 REQ-002／REQ-003 的做法，已直接對目前連線中的 Supabase 資料庫執行 `ALTER TABLE public.users ADD COLUMN IF NOT EXISTS phone_type VARCHAR(20)`；換資料庫或重建環境時需比照手動補跑。電話格式驗證邏輯統一寫在 `app/services.py` 的 `validate_phone_by_type`，表單(`app/forms.py`)透過共用函式呼叫，避免表單與服務層規則兜不起來(呼應本檔開頭「HTML 路由與 JSON API 路由都呼叫服務層」的既有原則)。目前僅套用在「帳號管理」建立教練帳號與學生自助註冊這兩個會寫入 `User.phone`/`phone_type` 的表單；「學生名冊」(`Student.phone`，`app/templates/students/form.html`)為獨立欄位與模組，不在本次「帳號管理」需求範圍內，故未變動。帳號詳情頁(`accounts/detail.html`)目前僅唯讀顯示連絡電話，尚無「編輯既有帳號連絡電話」的頁面/表單，此需求未提及故未新增。
